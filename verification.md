## Fix Email Verification Redirect and Booking Access

I have an existing Laravel + React car rental application with email verification.

### Current problem

When a registered user receives the email verification link and clicks **"Verify Your Email"**, the verification process does not complete correctly.

Instead of redirecting the user to the dashboard, the application currently redirects the user to the **"Resend Verification Link"** page.

I want you to fix the existing implementation without unnecessarily rewriting unrelated parts of the authentication system.

### Required behavior

After the user clicks the verification link from their email:

1. The verification token/link must be validated correctly.
2. The correct authenticated user must be identified.
3. The user's email must be marked as verified in the database.
4. The verification link must not be considered invalid when it is generated by the application.
5. After successful verification, redirect the user to the frontend **Dashboard**.
6. The user should remain authenticated after verification if the existing authentication architecture supports this.
7. The verified user must be allowed to book/rent a car.
8. The booking page/API must recognize that the user's email is verified.
9. The application must NOT redirect a successfully verified user to the **Resend Verification Link** page.
10. If the user is genuinely not verified, only then should the application show the resend-verification flow.

### Important: investigate the existing implementation first

Before making changes, inspect the complete existing verification flow, including:

* Laravel `User` model
* `AuthController`
* email verification controller/action
* verification routes in `routes/api.php` and/or `routes/web.php`
* authentication middleware
* email verification middleware
* Sanctum configuration if Sanctum is being used
* frontend authentication/verification pages
* frontend routing
* API client/authentication service
* dashboard route
* booking controller/service
* booking middleware
* database `users` table and the email verification column
* any custom verification-token implementation
* any custom verification URL generation
* `.env` values related to frontend URL/API URL if relevant

Trace the entire request from:

**Registration → verification email generation → email link → backend verification endpoint → database update → frontend redirect → dashboard → booking**

### Verify the database behavior

Check whether the application uses Laravel's standard email verification mechanism or a custom token system.

If using Laravel's standard verification system:

* Ensure the `User` model correctly implements the required email verification contract.
* Ensure the verification notification/link is generated using the correct Laravel mechanism.
* Ensure the verification route uses the correct verification parameters.
* Ensure the verification handler correctly calls the appropriate verification method.
* Ensure the user's `email_verified_at` field is updated.
* Ensure the verification request is not incorrectly protected by authentication middleware if the verification link is supposed to authenticate/identify the user through the signed verification URL.

If using a custom verification-token system:

* Trace where the token is generated.
* Trace where it is stored.
* Trace where it is included in the email URL.
* Trace how the backend validates it.
* Ensure the same token is being validated that was generated for the user.
* Ensure token expiration is handled correctly.
* Ensure the token is not being regenerated or overwritten before the user clicks the link.
* Ensure the user ID/email associated with the token is correctly resolved.

### Fix the redirect

After successful verification, the backend/frontend should redirect to the actual dashboard route used by this project.

Do NOT invent a new dashboard route.

Find the existing dashboard route and use it.

If the application is using a React SPA with Laravel API authentication, make sure the verification endpoint returns a response that the frontend can correctly interpret and then navigate to the dashboard.

If the verification endpoint currently redirects directly, make sure it redirects to the correct frontend URL rather than an API page.

### Fix booking access

After verification, test the complete flow:

1. Register a new user.
2. Confirm the user initially has no `email_verified_at` value.
3. Send the verification email.
4. Open the generated verification URL.
5. Verify the email.
6. Confirm `email_verified_at` is populated.
7. Confirm the user is redirected to Dashboard.
8. Navigate to the vehicle/car listing.
9. Select a car.
10. Start a booking.
11. Confirm the booking API does not reject the user because of email verification.
12. Complete the booking request.

If the booking system checks email verification using custom logic, fix that logic so it correctly checks the user's current database verification status.

### Also investigate the resend-verification page

Find exactly why the application currently sends successfully verified users to the resend-verification page.

Look for conditions such as:

```text
if (!user.email_verified_at)
```

or:

```text
if (!user.email_verified)
```

or frontend conditions such as:

```text
if (!isVerified) {
    navigate('/resend-verification');
}
```

Check whether the frontend authentication state is stale after verification.

If necessary, refresh/re-fetch the authenticated user's profile after verification so the frontend knows that the email is now verified.

Do not simply remove the verification check. The application must still prevent unverified users from booking if that is the intended business rule.

### Security requirements

Do NOT disable email verification.

Do NOT bypass authentication.

Do NOT accept arbitrary verification tokens.

Do NOT remove token expiration.

Do NOT remove signature validation if Laravel signed URLs are being used.

Do NOT mark users as verified without validating the verification request.

Do NOT expose sensitive tokens unnecessarily.

### Preserve existing functionality

Do not rewrite unrelated authentication, registration, booking, payment, vehicle, or admin functionality.

Make the smallest clean changes necessary to fix:

**Verification → Dashboard → Booking**
